## Day 5: Building an attacker AI agent (~2h47m)
Vladimir framed the week: Week 1 was foundations, Week 2 was manual attacks, this week moves to an
attacker agent that plans, attacks, judges and learns, and next week (Day 6) adds verification with
promptfoo. The deliberate pedagogy: give students a partly-built agent (not a from-scratch build, not a
full production agent), simple enough to understand the concept, then let them extend it with Claude
Code / Codex. Flow:

1. Homework show-and-tell (first ~45 min, Igor + Vladimir). A student reported the key homework finding:
   on Mercy Bank, entering no OTP correctly blocks a transfer, but entering any value as the OTP lets
   the transfer go through, even though the chatbot's text says it is not allowed. She confirmed via
   the `initiate_transfer` tool call (it fired regardless of the chat reply), reproduced it three
   times, then varied OTP shape (alphanumeric, dashes, short, valid-length) and all failed consistently.
   Her workflow: do the first test case the long way with ChatGPT to learn the process, then use Claude
   to generate and refine later cases faster. She had also set up the Week 4 app on Podman (her company
   laptop blocks Docker Desktop) and reused another student's system-prompt-leak prompt against it,
   finding a gap there too. A second student shared GitHub optimizations for running Mistral locally,
   plus a Firefox aha moment (use the IP address instead of `localhost`; Firefox tries IPv6 first and
   adds 1-3s latency). Vladimir noted, as a teaching aside, that the newest frontier assistant models
   refuse security / jailbreak-style requests much more aggressively than slightly older ones, so this
   coursework often means falling back a model generation or using open-source models. A reproducibility
   note recurred: attacking through a commercial model's API can get an account flagged or banned (both
   instructors were banned by OpenAI while building this exact system, then reinstated after explaining
   it was security testing).

2. Careers block (Igor + Vladimir, with a student sharing). The student had started a new role (AI
   evaluation lead) despite a posting asking for 4 years of experience; her interviewer openly
   acknowledged the requirement was unrealistic for a field this young. Takeaways pushed hard by Igor
   and Vladimir: do not be scared off by job titles or years-of-experience lines (the AIVSS doc is less
   than a year old, so "5 years" is nonsense), read the actual description and map your labs to it, look
   for what is common across a set of postings, network with the practitioners who built the field, post
   2-3x/week, and read arXiv papers to show you see where the field is going. Several live postings were
   screen-shared. Igor also reported a CIO/CTO dinner where C-level leaders were, in his words, largely
   unaware of agentic-AI risk, which he framed as proof of growing demand.

3. The attacker-agent concept (Vladimir, with a diagram). The engine runs in episodes, each a six-stage
   loop: **Wake -> Orient -> Plan -> Attack -> Judge -> Reinforce**. Wake/Orient load memory (what
   worked before) and check the target is alive; Plan picks which attack family to try next; Attack
   runs it (single-shot, then multi-turn up to a max-turns cap to avoid infinite loops); Judge flags
   whether it is a real bug (done in code for now, contains / not-contains style, later swappable for
   LLM-as-judge); Reinforce writes results to memory (files on disk) so the next episode is smarter and
   avoids duplicates. Important caveat Vladimir stressed: in this simple version there is no LLM inside
   the stages at first; it runs as a fixed script, and the point is to grasp the architecture before
   adding models. The planner uses UCB1 (upper confidence bound) to balance exploiting a winning family
   vs exploring untried ones; one group dug into this and explained it well. Named config knobs: max
   turns, attack delays, episode count, UCB parameters, all editable in `.env` / code.

4. Exercise 1 (paired/trios, ~30 min): run the target and the attacker in two terminals. Clone the repo
   fresh, prep Mercy Bank (`.env`, `npm install`, `npm start`) in terminal 1; in terminal 2 run the Week
   3 attacker (`npm run clean` to wipe prior state, then `npm start`). At this stage the attacker has no
   model configured, so it runs from hard-coded scripts. Task: watch one full episode, write one line
   per stage, inspect the `campaign/` output files (hits/misses, strategy register JSON with tries/wins
   per family, lessons), and answer "after a family wins, does the planner try it again or move on, and
   why?" Friction surfaced on return: several groups could not find any Wake/Orient info in the output;
   one trio got through the high-level stage descriptions but got stuck on what "turns" meant and how
   the agent decides to give up, and could not tell how to see the memory fill up. Vladimir's computer
   froze briefly mid-demo. The repetition-and-confusion was framed by Igor as intentional ("we need to
   find out what you don't understand").

5. Exercise 2 (paired, ~30 min): enable a real model on the attacker so it writes its own next moves
   instead of replaying a script. Copy `.env.example` on the attacker, point the target URL at local
   Mercy plus the Mercy lab key, and set the attacker's "brain" to any OpenAI-compatible endpoint.
   Vladimir demoed with GPT-4o Mini via OpenRouter (polite and weak, i.e. a poor attacker but fine to
   prove the wiring). Task: swap in different models and answer why you should point the attacker at a
   local / red-team model rather than a commercial one, plus name one strategy that needed adaptation to
   land and one that resisted. On return: one student paid for a RunPod Mistral 7B pod and got it wired
   after fixing the local URL; the live model tried harder on previously-unbroken episodes, but still
   could not break the chain and prompt-leak categories even with Mistral. Another student, on local
   Llama 3.2, did break the chain category that Mistral could not (same target, different attacker
   model, different outcome). A third student removed the hard-coded opening prompts from `strategies`
   so every attack prompt became model-generated and unique, and added a 502 retry (mirroring an
   existing 429 retry). One group got the same pass/fail pattern across models but gave the clearest
   articulation of why local models matter for attacking: no ban risk, lower/no token cost, no rate
   limits, reproducibility, and air-gapped / no-internet enterprises (legal/health/fintech) that cannot
   reach a commercial API at all. Another group saw no new vulnerabilities from adding a model; chain
   and prompt-leak never succeeded for them either. Vladimir closed on how to pick a model (start from
   frontier labs, survey open-source via Hugging Face by downloads/variants, compare with promptfoo),
   the difference between a direct provider key and OpenRouter (one key, all models, plus its own
   router/decision model), and previewed two advanced ideas (an agent that swaps multiple models
   internally, and a non-LLM "decision model" referred to in-session as "Jeff"/"TypeSafe") as news to
   watch, not taught.

Homework: none between Saturday and Sunday (deliberate rest). Midterm survey announced for Day 6.

## Day 6: Closing the loop - verify, gate, promote to promptfoo (~3h05m)
Vladimir ran the day as mostly breakouts (trios) with less lecturing, after the class voted to keep
groups of three. Igor opened with a long motivational framing: the program is "transformational," the
cohort builds lasting peer communities, and the explicit end-goal is a job, so from here it is
"practice, practice, practice." The midterm survey was posted in the Day 6 thread and students filled it
live at the start. Flow:

1. A student's share: a goal-hijacking prompt injection on Mercy Bank found with NVIDIA's Garak scanner,
   run slowly and within the rules of engagement (not the default hundreds of requests) to avoid
   overloading the target; a "goal hijacking" probe made the bot print attacker-controlled text once the
   payload was adapted to Mercy Bank. Igor and the student contrasted Garak (NVIDIA, red-team /
   assessment kit, good when you are an outside pen-tester with no internal access) vs promptfoo
   (OpenAI, more universal, better when you own the system). Igor noted Engenious uses Garak
   professionally.

2. The OpenAI incident (Vladimir). He shared, as proof of why this field matters, an OpenAI disclosure
   that its agents posted 53 cases of user-uploaded images to third-party image-hosting sites. His
   framing: even with training opt-outs, the risk is models/agents acting on and exfiltrating user data
   to third parties; this is the kind of real incident students should reference in interviews. Note:
   this is an instructor's in-session characterization of a news item, not independently verified here.

3. Block 4 carryover (custom strategies). Students add their own attack strategy to the agent: a
   strategy is a combined object with an opening message, escalation / follow-ups, family, OWASP IDs,
   and a goal the judge must prove. Task: add one custom strategy, run, confirm it appears in a new
   episode, then play with the episode / max-turns knobs to try to crack a category that held on Day 5.
   One student reported a concrete win: using Claude's planning mode she added one extra chaining
   strategy that broke the chaining category that had resisted on Day 5. Another group discussed
   splitting a multi-strategy family into separate strategies so you can see which specific strategy in
   a family actually scores.

4. Closing the loop - verify + gate + promote (the core of the day). The new `npm run verify` re-runs
   each candidate finding 3 times in parallel, each from a fresh session, and a gate (default 3-of-3)
   decides whether a finding is confirmed (promoted) or rejected (dropped). Fresh sessions matter
   because a warmed-up session could already hold the canary in context and fake a leak. Confirmed
   findings are auto-written as promptfoo YAML regression files into `campaign/regression/`, which can
   then feed a CI/CD regression suite. One student changed the gate to repro-runs=5 / min=3 and realized
   this quietly lowers the bar to 60% (not the same as 3-of-3 = 100%); at 5/5 a borderline finding was
   rejected again. She then had Claude modify `verify` (a ~3-line change) to run one finding ID at a
   time so she could re-run a single finding many times for a real reproduction rate. On a 100-run
   single-finding test, `inject-recovery` reproduced ~55% of the time; Vladimir said he would still
   report it because of its impact, which drove the day's central lesson: the gate is a judgment call
   where impact matters as much as frequency (one student: a credit-card leak once in 100 runs is still
   critical and should be fixed first; frequency sets priority among equal-impact findings). The same
   student read the verify code: a `baseline_is_agentic` function re-asks a model whether the leak
   reproduces without the agentic attacker; if the model still leaks with no attacker connected it is
   non-agentic, otherwise agentic. The `impact` line is a hard-coded dictionary (e.g. agency-fake-OTP =
   critical), not an algorithm; Vladimir confirmed this is deliberately simple code for now, to be
   replaced later by an LLM/agent that decides impact and verdict.

5. Portfolio / GitHub guidance (a student asking, Igor + Vladimir + another student answering). A
   well-organized GitHub repo is now the primary hiring asset; last cohort's survey called the repo the
   single biggest takeaway. Recommended practice: a branch per exercise, several clear commit messages
   per exercise, one README with a running changelog, keep old branches so an interviewer can walk the
   timeline, do not commit run results (demo those live). Hiring teams now review GitHub history, often
   by running an AI agent over the repo.

6. One student's extended "what is the point" exchange. She repeatedly and candidly said she could do
   Exercise 2 but did not understand its purpose. After several reframings the resolution landed: the
   step is a manual judgment of which finding is strongest, because that candidate is what gets coded
   into promptfoo as a regression test; there is no single right answer, it is subjective to the
   business case. Igor praised the honesty and both instructors conceded the exercise framing was
   confusing; Vladimir said he will likely merge this exercise with the verify/gate step for the next
   cohort so students go straight from the gate to promptfoo and see the payoff.

Homework (for the week, revisited next Saturday): redo Blocks 3 and 4 from scratch but go further than
the written steps (explore, change code, add a model to the judge, break and re-clone freely). Core
task: take gated findings and report them into promptfoo so the loop closes and a CI/CD promptfoo suite
guards against regressions. AIVSS scoring ("score and ship") is lower priority and points back to the
Day 2/3 explanation; it was not reached live.

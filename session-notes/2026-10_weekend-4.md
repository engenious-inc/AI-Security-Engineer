## Day 7: RedCell, the advanced attacker agent and its dashboard (~3h03m)
Low turnout at the start (four, then five people at the 3-minute mark), rising to roughly eight to nine
for the breakouts. Three attendees were listen-only; one student left before the breakouts. Flow:

1. Opening (Igor, then Jaime). Igor framed the course as "a path, at least a year," rather than a
   silver bullet. Jaime reported from the WeAreDevelopers World Congress (attended with his employer as
   a sponsor): AI and AI security were everywhere, but QA/quality vendors were nearly absent, which he
   framed as an opportunity; nobody he asked had attacker agents in production, though some liked the
   idea; a DevOps-security vendor called CI/CD pipelines "the biggest door" for attackers (access to
   code, API keys, tokens). Igor added that the AI-security vendors he meets focus on incident response
   after the fact, while this cohort works on prevention.

2. Show-and-tell (most of the first hour). One student said the pace jumped when the course moved to
   building agents, and she spent the week on Claude Code fundamentals instead of the homework; Vladimir
   agreed pre-cohort tutorials on Claude Code / Codex should be a "must" for the next cohort. Another
   student showed a job-capability tracker built with ChatGPT (20-30 job postings mapped to 35
   capabilities, with an evidence column and a generated roadmap) and her course portfolio repo with the
   Engenious repo as `upstream` and branches per day. A third student finally leaked Mercy Bank's system
   prompt (one of two categories the class had not broken) by running a local Mistral 7B via Ollama as
   the attacker: lessons were build trust first, escalate gradually, never reveal intent up front
   (multi-turn); he argued a local model also lowers the risk of provider-policy violations, and plans
   to study RAG attacks next. A fourth student demoed her own extension of the Week 3 attacker:
   per-target YAML config, "oracles" (deterministic checks) and "behaviors" (openings, follow-ups,
   hints), custom npm audit commands, Mistral 7B as the auditor model, a detailed console log, a verify
   step that re-runs claimed hits, an HTML summary, and a "profile + adapter" design so the same engine
   can target other apps. Vladimir: "half of today's material" already done by this student.

3. Meet RedCell (Vladimir, after a break). RedCell (pushed to the repo the same morning as
   `labs/attacker-pro/`) runs a ten-stage loop: wake, orient, plan, attack, judge, reinforce (the
   campaign loop), then verify, score, promote, report (closing the loop). Every stage has a
   deterministic code path and an optional LLM "brain" (recon, strategist, attacker, judge, report). It
   runs offline against a mock adapter with no key, or against the real Mercy Bank. Controlled from an
   HTML dashboard (`npm run dashboard`, localhost:8787): set the target and the attacker brain
   (OpenAI-compatible via OpenRouter; he demoed GPT-4o mini and asked students to try Mistral 7B or 3B),
   campaign settings (strategies, number of episodes, reproduction bar), a live-run terminal view,
   findings sorted critical / medium / low (confirmed vs rejected after reproduction), separate
   developer and executive reports, and promptfoo embedded so confirmed findings are promoted to
   regression tests without leaving the dashboard. Vladimir said he made the dashboard "ugly on purpose"
   so students would rebuild it; he also suggested adding a human-in-the-loop approval stage if a
   company requires it.

4. Block 2 exercise, "Meet RedCell" (groups of four, planned ~30 min, ran ~40-48 min). Setup (clone/pull,
   run Mercy Bank in one terminal and the dashboard in another), then Round A on mock data and Round B
   with a real LLM.

5. Debrief: decoding the live-run output (most of the last hour). Finding cards: the objective was
   visible and the orchestrator was the "crescendo" or "ladder" tag, but the converter did not appear on
   the cards. Vladimir confirmed converters are not yet tagged on findings; a converter transforms the
   message before sending (e.g. Base64) to slip past guardrails. One student found a Base64 tag where a
   converter had actually been used. The "full bar": two students showed it was not wins/pulls (6 pulls,
   2 wins still showed full); the explanation that landed is that it is the bandit planner's priority
   score for which attack family to try next (untried families get top priority; families that keep
   hitting stay high; families that miss drop). Vladimir conceded "probably I have some bug here" and
   the bars are not 100% accurate to the underlying numbers. Objective vs family vs strategy: Jaime's
   analogies (break into a file cabinet: the objective is the cabinet, families are the ways in; then a
   casino: families are slot machines, the bandit balances exploring new machines against exploiting
   ones that pay). One student's one-sentence summary was accepted: each episode has one objective (e.g.
   PCI = full card number, BOLA = another customer's data) and one strategy (e.g. `bola-linked`), and
   the planner ranks the families (access control, sensitive data, chain, encoding) by past success.
   Another student (who had rewritten the Week 3 attacker in Python) asked whether this design is
   industry standard; Jaime: no cookie-cutter framework exists, attacker agents are new, build for your
   audience and rely on solid coding standards.

Homework: use Claude Code to rewrite the live-run terminal output so it makes sense to you (explain
objective, family, strategy; replace or annotate the bars with numbers); read the student guide, the
repo's `PLAN.md` architecture file and its strategy matrix; start thinking how to adapt the agent to
another app (the Week 5 ticketing system) as portfolio material.

## Day 8: Customizing RedCell, mock vs real, first stakeholder report (~2h09m)
No Igor today; Tagir ran the rooms. Several attendees were again listen-only, and one student said she
had not done the homework. Flow:

1. Opening talk (Tagir, prompted by Jaime and Vladimir). Enterprises are moving to open-weight models
   hosted in their own cloud (AWS in Tagir's case) because commercial token prices keep rising, with a
   proxy router that sends simple tasks to cheap models and planning to stronger ones; production
   features usually stay on a locked model.

2. Recap and expectations (Jaime). Mercy Bank, the basic attacker, now RedCell: the demos are a
   starting point, not what you will use on the job; fluency with an AI coding assistant is a must. He
   posted Anthropic's Skilljar courses (Claude Code 101 / in action) to the Day 8 Discord thread.

3. Homework show-and-tell: customized dashboards. One student used ChatGPT to write prompts for Claude
   Code and to translate its answers into plain language, step by step; she added an architecture doc, a
   glossary and quick-reference, planner rankings in place of the bars, and colour / episode separation.
   Another student (four hours of work) added a campaign drop-down, status bars, a formula display for
   the family ranking, a table version of the event log, and merged her own audit framework (its
   verification table) into RedCell. Jaime showed his own small changes: hover explanations per
   strategy, percentages and "tries / succeeded" instead of pulls/wins, "round" instead of episode with
   a plain goal description, a fix for duplicate findings (confirmed and rejected versions of the same
   finding both showed), a glossary tab, and a promptfoo regression-runs view.

4. Exercise, peer-led breakouts (~30 min). Two rooms, two students as "captains" walking their groups
   through how they used AI tools. One student built search, filters and a jump-to-latest/tail mode for
   the logger during the session (~20 min, starting from asking Claude "what would you improve?");
   Vladimir pointed out this student was using Claude in Chrome as an MCP so Claude Code could click
   through and verify its own UI changes.

5. Block 3 exercise (3A and 3B, each run first with the mock adapter, then against Mercy Bank, ~30
   min). Jaime explained mock (scripted demo responses, no tokens) vs the Mercy Bank adapter, and code
   mode vs LLM mode for the attacker's brains. One group's Base64-encoded attack hit the mock but held
   against Mercy Bank, because GPT-4o mini decoded the payload, reasoned about intent and declined;
   Vladimir: that is exactly why the mock exists, so students see a hit even when the real target holds.
   Claude Code in the VS Code panel could not see the IDE terminal output; Vladimir showed running
   commands with `!` inside the Claude Code CLI so the output lands in its context. Per-stage models:
   the dashboard uses one model for every stage; Vladimir suggested making recon, strategist, attacker
   and judge selectable separately, mostly with smaller models, and possibly non-generative "decision"
   models for judging. Cost-cutting path (Vladimir, answering two students): collect 50-100 good
   input/output samples from a strong model, expand them into ~500 synthetic samples with a model like
   Qwen, train a small (~2B) model and swap it into one stage; he experiments on Modal and said Claude
   Code can drive it, framed as "a bit early" for this cohort. Another student asked one agent per
   target vs one general agent: Jaime compared it to promptfoo's per-industry plugins; Vladimir
   recommended one shared technical foundation with domain-specific content (a "swarm"), confirming this
   is how Engenious adapts its agents to clients, starting from the intake questionnaire.

6. Career aside (in the break). A student asked for resume help. Vladimir: your GitHub is your main
   resume, post drafts in Discord for review. Jaime: keep a few role-family resumes with matching
   keywords rather than one per posting.

7. Block 4 plus first stakeholder report (~30 min, merged to save time). Run 4A/4B (mock and real),
   then present findings "as to a C-level": rates and risk levels, high vs low risk areas, what to fix,
   in any format. Only one student presented: she had an agent merge her campaign reports into a PDF,
   used ChatGPT to fix the layout and check it against stakeholder-reporting best practices, and asked
   it for talking points. Her top finding: money transfers without OTP, which she ranked above its AIVSS
   score. Nobody else volunteered; Vladimir: "that means homework."

8. Next week's target (Jaime, last ~15 min). The ticketing app (`ai-security-chatbot/`, a fictional
   cables-and-chargers store called NodeLine Tech, run via Docker): login, chat, tickets with urgency and
   status. He demoed an indirect prompt injection planted in a ticket subject line, then calling
   `localhost:5000/api/chat` in Postman and intercepting the same request with Burp Suite (Community)
   plus FoxyProxy in Firefox and resending it through Repeater. Exposure only, as traditional
   pen-testing context. Next Saturday covers manual attacks and prompt templates on this app, plus the
   ROE and the intake questionnaire; Oct 10-11 is the final weekend.

Homework: explore the ticketing system as a normal user (exploratory testing, recon and fingerprinting:
payload shape, response fields and times, ticket ids, RAG or not, tools or not); try indirect prompt
injection through tickets; plan how you would build or adapt an attacker agent for it; set up Burp Suite
+ FoxyProxy; read the ROE and the intake questionnaire; finish the stakeholder report if not presented;
keep practicing with Claude Code.
